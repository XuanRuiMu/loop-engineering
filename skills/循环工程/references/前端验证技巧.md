# 前端验证技巧（实战坑 · 纯说明性）

> 来源：某前端项目 FP 修复任务（2026-08-12）Self-Harness 元循环挖掘。
> 修改级别：待确认（包含验收门和凭据约束，不得自动改动）。

## 1. 浏览器自动化脚本的模块解析

- 验证脚本放在任务工作区内，优先与项目依赖配置同层，并使用项目实际的模块导入方式。
- 宿主或模块系统不支持普通导入时，使用运行时提供的绝对模块URL机制；不要在文档中硬编码某台机器的盘符或项目路径。
- 截图落盘 `.agents/evidence/traces/<功能点>-<页面>-<YYYYMMDD>.png`，同名 `.md` 记录DOM指标；禁止只贴图不落盘。

## 2. 截图落盘为主、读图复核为辅

- 前端功能点验收以落盘截图、DOM文本断言和过滤后控制台错误计数为机器证据；读图复核只作补充。
- 模型或宿主不能读取图片时，以DOM文本、布局尺寸、溢出检查和像素扫描继续验证，并在遗留中明确未做视觉复核。
- 可用DOM/Canvas代理证据：`getBoundingClientRect`、`offsetWidth`、`scrollHeight`、CSS变量、`<canvas>.getContext('2d').getImageData()`像素扫描。

## 3. 远程上传的凭据与网络约束

- 远程上传优先使用项目已经提供并验证过的安全封装；不存在时使用宿主正常的版本控制认证流程。
- 禁止把令牌直接写进命令、日志、证据或版本历史。
- 网络重置、认证失败和权限不足必须记录为环境限制或权限问题，不得伪装成代码验证通过。

## 4. 控制台过滤（只拦 error，放行 warning）

- 前端验收的控制台门只统计 `error`，`warning` 一律放行；多页 pops/异步日志先在 FP 验收标准里写明白白名单，无白名单定义时不得以 warning 判失败。

## 5. DOM 必填指标与写入位置

- 每个前端FP的同名 `.md` 必须含：页面 URL、视口尺寸、关键容器 `getBoundingClientRect`、有无横向溢出、过滤后控制台 error 计数；缺任一项视为证据不全。

## 6. 全量测试 flaky 三段判定与文件级隔离

- 全量失败但单文件稳定通过时，先建立任务前基线：可用版本控制时隔离本任务改动，不可用时使用独立副本、文件清单或哈希快照。基线同样失败才按既有flaky处理。
- 再串行复核单文件和组合文件，确认业务路径真实通过；最后只修复确认属于flaky的测试，不改业务行为迎合结果。
- 多个`render`同一组件的测试文件应隔离渲染状态；长耗时用例使用项目已有超时机制；跨组件文本匹配应限定查询范围或使用全匹配。

## 7. 视觉验收必须是独立工人，且不与实现混派（2026-09-19 十四项缺陷修复任务实战）

- 反例：把"修一个线上 500"与"8 项浏览器取证"混派给同一工人，两个目标互相挤占轮次，双双未收口，且主代理无法判断哪一段先做完。
- 规则：取证/验收一律单独派发；单工人验收面 ≤3 个；实现工人只负责"改前/改后截图 + DOM 断言"这类最小证据，跨页面多视口的完整取证交给验收工人。
- 派发给验收代理的提示词要控制体量。若宿主明确拒绝单次请求体，按投递失败处理：缩短提示词或拆分任务后重派，不把它误判为功能阻塞，也不依赖任何固定错误文本。
