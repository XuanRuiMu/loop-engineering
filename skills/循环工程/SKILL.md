# 循环工程

## 定位

循环工程是父级编排器，不是业务实现、测试或审查技能。它负责目标、功能点、状态、代理调度、预算、恢复、证据和最终门；实际能力由专项 Skill 提供。

核心目标是用更多但可控的独立上下文换取稳定性，而不是单纯增加 token。

## 开始前读取

|角色或时机|必须读取|
|---|---|
|主代理启动或恢复|`PROGRESS.md`、`BUDGET.md`、`references/EnvironmentEngineering.md`、`references/Orchestrator-Headless模式.md`|
|派发独立代理|`references/子代理提示词模板.md`、当前功能点、`PROGRESS.md`|
|开发、修复或测试|`代码需求实现器`、`Bug修复`、`软件测试`|
|方案或实现审查|`方案审查`、`三轴审查`|
|需求含糊、架构选型、跨模块改动或高风险决策|`references/推理增强.md`|
|方向卡住|`纾困复盘`|
|维护本 Skill|`HARNESS.md`、`EVIDENCE.md`和回归任务集|

首次运行时 `PROGRESS.md` 不存在，先按 `references/PROGRESS模板.md` 初始化，再派发任何代理。

## 不可破坏的规则

|规则|要求|
|---|---|
|状态外置|当前推进所需信息只保存在 `PROGRESS.md`；每轮重写快照，不追加历史。|
|状态极简|完成项立即删除；过期、重复、失效信息立即替换或删除；正常任务建议控制在40至70行。|
|单写者|主代理独占写入 `PROGRESS.md`；独立代理只读并返回摘要。|
|优先独立代理|宿主支持独立代理时优先派发；不支持时主代理补位并记录能力降级。|
|范围受控|权限默认开放，但不得自行扩大目标、范围或验收标准。|
|用户WIP保护|启动基线中已有的用户修改不得回退、覆盖或顺手修复。|
|高危操作提醒|凭据、部署、外部系统、不可逆操作、核心规则和破坏性版本控制操作先用通俗语言说明影响并确认。|
|可验证完成|完成必须同时满足验收命令、证据、审查和主代理最终门；口头声明不算完成。|
|三态验证|结果只能是“通过”“环境限制”或“真实失败”；环境限制必须给出可复现证据。|
|修复阶梯|同一真实失败按 `BUDGET.md` 的 `per_fp_attempt_limit` 递增修复次数；中段必须换方法，达到上限后停止并标阻塞。|
|stall分类|空摘要、无验收推进、重复索要已有决定或未完成收尾才算 stall；真实失败不得伪装成 stall。|
|方向性假设|会改变行为语义、范围、公开契约或用户权限的决定必须停止并交用户确认。|
|防假完成|主代理必须复跑受影响门禁和最终门，不能只信代理摘要。|
|嵌套代理计数|预算按实际创建的代理实例计数，包含审查代理和重派代理；Worker必须回报嵌套数量。|
|独立性不可伪造|三轴审查、BlindSpot和核心提案反对审查必须有独立上下文；主代理补位不能冒充独立审查。宿主无法提供独立上下文时返回“环境限制”并阻塞该门禁。|
|推理门|按需执行 `references/推理增强.md` 的G1、G2、G3；结论必须有外部证据，推翻条件必须写明。|

## 跨宿主能力适配

循环工程只定义语义职责，不绑定任何宿主的工具名、参数名或代理类型。开始时根据宿主实际能力选择路径：

|能力|有该能力时|没有该能力时|
|---|---|---|
|独立代理|用统一提示词派发短生命周期代理|主代理串行补位|
|并行代理|无冲突功能点并行派发|改为串行|
|用户交互|用宿主交互能力展示问题和选项|在普通回复中清楚列出待确认事项|
|版本控制|使用仓库提供的比较、回退和提交能力|使用启动快照、文件清单和哈希差异|
|步骤或轮次限制|读取实际限制并写入预算|保持未知，不猜测固定数值|
|后台任务|使用宿主原生后台机制并在返回前回收|不创建无法回收的后台任务|
|token统计|使用宿主返回的实际值|保持未知，不用字符数冒充精确token|

提示词中可写“启动独立代理”“并行启动三个审查角色”等自然语言要求，不得写某个宿主的私有函数签名。

## 四阶段工作流

### 阶段1：定义目标

1. 阅读用户目标、项目规则、必要源码和现有状态。
2. 把目标改写为可验证结果，明确验收命令、非目标和用户WIP。
3. 目标含歧义、跨模块改动、架构选型或不可逆操作时，按 `references/推理增强.md` 执行G1澄清门，每个任务只做一次；不满足触发条件时跳过并在确认目标时说明原因。
4. 设定 `BUDGET.md` 中的循环、代理实例、修复、stall、补位和墙钟预算。
5. 建立启动基线：可用版本控制时记录基线与工作树状态；否则记录关键文件清单和哈希。
6. 通过宿主可用的用户交互能力确认目标；不能交互时，在普通回复中给出待确认项并停止依赖该决定的步骤。

### 阶段2：拆解与初始化

1. 拆成粗粒度、可独立验证的功能点；一个代理一次承担一个完整功能点。
2. 每个功能点写明目标、机器验收、依赖、范围和状态。
3. 用 `references/PROGRESS模板.md` 创建或覆盖 `PROGRESS.md`。
4. 删除重复、无关和失效信息；正常快照建议40至70行。
5. 通过宿主可用的用户交互能力确认功能点表；不能交互时返回“待用户确认”。

### 阶段3：自主循环

#### 每轮启动

1. 读取 `PROGRESS.md`，确认下一步、计数、活跃代理、用户WIP和未决事项。
2. 检查目标、停止条件和全部熔断条件。
3. 选择依赖已满足的功能点；依赖项显示完成时仍需复跑适用门禁。
4. 派发前估算 `per_fp_turn_estimate`；超过 `fp_split_threshold` 时拆成实现、取证或收尾任务。

#### 派发

1. 使用 `references/子代理提示词模板.md`，显式传入 `headless_mode=true`。
2. 把已核实事实和主代理推断分栏；代理必须先证伪推断。
3. 独立代理完成实现、局部验证和适用审查，只返回结构化摘要。
4. 主代理核对摘要、证据、实际改动和门禁结果后才能更新状态。
5. 功能点命中G2触发条件时，先按 `references/推理增强.md` 写出反例或不变量、迁移边界和隐藏验收场景，并把结论写进派发提示词；判定命中时必须写出命中的具体条件，未命中时在提示词写“推理门：无”。

#### 失败、stall与补位

1. 真实失败按修复阶梯处理；环境和权限问题单独分类。
2. stall 重派必须使用新上下文并改变方法；宿主未返回完整收尾信息时按 stall 处理，不依赖特定错误文本。
3. Worker返回“待用户确认”时，把该功能点改为待确认、暂停该功能点派发，并把问题、选项、影响和证据交主代理；不得按stall重派，也不得代答。
4. Worker无法建立独立审查上下文时必须返回环境限制，主代理不得把自身补位记为独立审查。
5. 主代理补位前后都执行适用门禁，并计入补位预算；单次补位估算超过 `fp_split_threshold` 时必须先拆小。
6. 达到补位上限后停止继续补位；仍有独立代理能力时改派新代理，否则报告当前阻塞。

#### 并行与契约

1. 只有无依赖、无文件冲突、无资源冲突且收益高于协调成本时才并行。
2. 同一工作树同一时刻只允许一个共享门禁持有者。
3. 公开契约变化只在 `PROGRESS.md` 保存尚未被消费者吸收的“旧值到新值”增量。
4. 并行前扫描契约；能序列化则串行，必须并行时把增量注入每个消费者。
5. 消费者完成、跳过或不再需要该增量后立即删除对应行。

#### 每轮收束

1. 验证证据和实际树状态。
2. 覆盖更新 `PROGRESS.md`；完成功能点直接删除，不保留完成历史。
3. 只保留仍影响下一步的未决事项；问题解决后立即删除该行。
4. 主代理补做代理因宿主能力缺失而未执行的独立审查门禁；无法建立独立上下文时不得标为通过。
5. 所有代理和后台任务结束后才能运行共享最终门。

### 阶段4：验证与交付

1. 确认没有“待开始”或“进行中”功能点，且所有代理和后台任务已结束。
2. 主代理串行复跑全量测试、构建、lint及项目已有发布检查。
3. 按 `references/推理增强.md` 执行G3校准门：给出置信度、支撑证据和推翻条件；无独立证据的项标为未验证。
4. 核对用户WIP、实际改动、证据、残留进程和未决事项。
5. 状态为“熔断”或“阻塞”时跳过Self-Harness；其他状态先检查是否存在新的、可复现且可跨任务复用的弱点。
6. 在判定“没有新弱点”前，必须由独立审计者确认；同一主代理的自评不能替代。宿主无法提供独立上下文时，将未完成项写入遗留而不是宣称无新证据。
7. 触及核心流程、预算、权限或返回契约的提案必须经过独立反对审查；待确认项交用户决定。
8. 通过宿主可用的用户交互能力交付；不能交互时用普通回复报告完成项、验证项、遗留问题、置信度、支撑证据、推翻条件、未验证项、降级情况和下一步。

## 恢复

1. 读取 `PROGRESS.md`；不存在时不得凭对话记忆猜测任务状态。
2. 核对启动基线、用户WIP、实际文件状态、活跃代理和后台任务。
3. 对“进行中”功能点重跑最小基线；只有确认没有半成品或冲突后才可重置为“待开始”。
4. 用户WIP、来源不明改动或权限决定不得自动清理或覆盖。
5. 恢复过程只更新当前快照，不记录恢复历史。

## 专项 Skill 组合

|场景|调用|
|---|---|
|需求或方案不清|`方案审查`|
|复杂需求文档化|`生成PRD`|
|新功能或小范围实现|`代码需求实现器`|
|Bug修复|`Bug修复`|
|测试与回归|`软件测试`|
|实现后审查|`三轴审查`|
|循环卡顿|`纾困复盘`|
|跨会话摘要|`会话交接`|

所有专项 Skill 都必须接受 `headless_mode`。缺少该模式或缺少独立审查能力时，必须返回环境限制，不得伪造完成。Headless 模式只改变交互和交付通道，不降低测试、审查、翻译、安全或验证要求。

## Self-Harness

Self-Harness 采用触发式而非每任务强制深循环：

1. 只从本轮真实失败、审查遗漏和环境问题中提炼新的、可复现且可跨任务复用的弱点。
2. 判定“没有新弱点”前必须由独立审计者复核；主代理自评不能作为停止依据。
3. 有新证据时先判断是否已被现行规则覆盖；已覆盖则不重复提案。
4. 纯格式或说明性修正可在备份后应用并运行回归。
5. 触及核心流程、预算、权限或返回契约时，先做独立反对审查并交用户确认。
6. 提案验证必须运行完整回归任务集：`python -B references/harness-test-suite/run_all.py`；失败立即回滚。

## 维护

运行时只按需读取本 Skill 的主文档、当前状态和直接相关参考，不读取历史证据或维护测试。维护时使用 `references/harness-test-suite/manifest.json` 中的固定任务清单，禁止动态发现或按“至少N个”判定通过。
